# Jev 战术接入讨论稿

## 接入时点

0.18.0 实机只需确认三项：长距离探索能持续移动、地面长矛与牛毛能被发现并捡起、火炬余量足够时夜间继续行动。达到这三个执行器基线后即可接 Jev；首夜全自动生存无需先做到完美。候选和提示词现在就可以讨论。

## 每次决策的数据

桥接服务在动作完成、出现重要新资源、目标受阻时生成一组具体候选。每项包含 `candidate_id`、动作类型、目标 GUID 或坐标、预计收益、时间／距离、当前风险和失效条件。状态摘要包含白昼阶段、饥饿与生命、火炬剩余秒数、库存空格、当前目标、最近失败原因。观察列表只使用 Mod 上报的局部实体。

示例候选：

| ID | 执行动作 | 条件 |
| --- | --- | --- |
| `pick_spear_123` | 捡 GUID 123 的长矛 | 目标仍在附近、有背包空格 |
| `collect_flint_456` | 走向 GUID 456 的燧石并拾取 | 路线可走、目标仍可见 |
| `explore_east_7` | 沿东侧已知可通行点持续探索 | 无迫近危险、照明余量充足 |

给 Jev 的 `choice` 问题只选择一个 `candidate_id`。`instructions` 说明当前任务，例如“在确保今夜照明的前提下，选最有利于建立基本工具与继续探索的下一项；已经安全执行中的移动优先继续”。每个 `criteria` 说明候选的实际收益与代价。状态和候选都带同一 `candidate_set_id`、世界 GUID、观察序号；回复回来后桥接重新检查目标有效性，再映射成现有的 `MOVE_TO_TARGET`、`MOVE_TO_POINT`、`PICKUP_TARGET` 等命令。

## 调用节奏

- 本地安全逻辑持续处理黑暗、火炬耗尽和迫近威胁。
- 只有两个以上合理候选且取舍可能改变结果时才调用 Jev。持续行走时按本地观察处理路边拾取，无需每半秒请求一次模型。
- 提供规则、mock、Jev 三种可替换选择器；记录候选集、最终选择、延迟、用量及动作结果，便于比较。
- 首轮真实 API 采用有限调用次数和预算；API 密钥只保存在本机 Python 环境中。

当前 TypeSafe API 使用 `POST /v1/systemone`，请求包含 `state`、`model` 和 `questions`；`choice` 的 `criteria` 由程序列出选项，返回选中的键及概率分布。具体请求字段以接入时的官方文档复核。
